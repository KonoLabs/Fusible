# Firmware Bridge & `pins.rs` Generation

Fusible bridges the gap between hardware schematic layout and embedded firmware by generating typed Rust bindings (`pins.rs`) directly from the circuit netlist.

---

## 1. How the Bridge Works

```
┌─────────────────────────────────┐
│     hardware/index.tsx          │  Declarative circuit with MCU & peripheral nets
└────────────────┬────────────────┘
                 │ fusible check / fusible build
                 ▼
┌─────────────────────────────────┐
│      Fusible Netlist Graph      │  Extracts MCU pins, port traces, signal names
└────────────────┬────────────────┘
                 │ Code Generation (if fuse intact)
                 ▼
┌─────────────────────────────────┐
│   apps/firmware/src/pins.rs     │  Typed Rust constants & peripheral structures
└─────────────────────────────────┘
```

1. Fusible inspects `fusible.yml` to identify the silicon target (e.g. `chip: esp32-s3` or `chip: stm32g431`).
2. It parses the microcontroller's `<chip>` in `hardware/index.tsx`, identifying its pins and trace destinations.
3. Power rails (`GND`, `VCC`, `3V3`, `5V`) and unconnected non-connected pins (`NC`) are filtered out.
4. For every connected GPIO, Fusible derives a deterministic Rust uppercase identifier (e.g., `STATUS_LED`, `CAM_D0`, `UART_TX`).
5. It groups related signals into peripheral structs (`UartPins`, `SpiPins`, `I2cPins`).
6. If the fuse is intact, it writes `apps/firmware/src/pins.rs`. **Never edit this file manually**.

## 2. Circuit TSX Conventions for Clean Rust Bindings

To ensure clean Rust identifiers in `pins.rs`, follow these naming conventions:

### Microcontroller Declaration
Use clean GPIO numbers in `pinLabels`:
```tsx
<chip
  name="U1"
  footprint="qfn48_w7_h7_p0.5"
  pinLabels={{
    pin1: "GND",
    pin2: "VDD3V3",
    pin3: "GPIO1",
    pin4: "GPIO2",
    pin5: "GPIO4",
    pin6: "GPIO5",
    pin7: "GPIO43",
    pin8: "GPIO44",
  }}
/>
```

### Trace Destinations
When connecting the MCU to a peripheral, the remote component name and port name are used to derive the signal:
```tsx
{/* Connects GPIO4 to D1.anode -> Generates STATUS_LED */}
<led name="LED1" color="green" footprint="0603" ... />
<trace from=".U1 > .GPIO4" to=".LED1 > .anode" />

{/* Connects GPIO43/44 to DEBUG_UART -> Generates UART_TX and UART_RX */}
<chip name="UART1" footprint="pinrow2_p2.54" pinLabels={{ pin1: "TX", pin2: "RX" }} />
<trace from=".U1 > .GPIO43" to=".UART1 > .TX" />
<trace from=".U1 > .GPIO44" to=".UART1 > .RX" />
```

## 3. The Generated `pins.rs` Output

The resulting `pins.rs` looks like this:

```rust
//! Generated by Fusible — Electronic Linter & Hardware Bridge.
//! DO NOT EDIT MANUALLY. Changes will be overwritten on next build.
//!
//! Board: fieldcam
//! Microcontroller: esp32-s3 (U1)

#![allow(dead_code)]

/// Hardware GPIO pin constants extracted from the circuit netlist.
pub mod gpio {
    /// Pin 4 (hardware net `.U1 > .GPIO4 to .LED1 > .anode`).
    pub const LED_ANODE: u8 = 4;

    /// Pin 43 (hardware net `.U1 > .GPIO43 to .UART1 > .TX`).
    pub const UART_TX: u8 = 43;

    /// Pin 44 (hardware net `.U1 > .GPIO44 to .UART1 > .RX`).
    pub const UART_RX: u8 = 44;

    /// Pin 8 (hardware net `.U1 > .GPIO8 to .BATT1 > .SENSE`).
    pub const BATT_SENSE: u8 = 8;
}

/// Peripheral pin mapping for `Uart`.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct UartPins {
    pub tx: u8,
    pub rx: u8,
}

pub const UART_PINS: UartPins = UartPins {
    tx: 43,
    rx: 44,
};
```

## 4. Consuming `pins.rs` in Embedded Firmware

### ESP-IDF (esp-idf-hal)
In `apps/firmware/src/main.rs`:
```rust
mod pins;

use esp_idf_hal::peripherals::Peripherals;
use esp_idf_hal::gpio::PinDriver;

fn main() -> anyhow::Result<()> {
    let peripherals = Peripherals::take()?;

    // Use typed pin constants
    let mut led = PinDriver::output(peripherals.pins.gpio4)?;
    led.set_high()?;

    Ok(())
}
```

### Embassy (embassy-stm32 / embassy-rp / embassy-executor)
```rust
#![no_std]
#![no_main]

mod pins;

use embassy_executor::Spawner;
use embassy_time::{Duration, Timer};
use embassy_stm32::gpio::{Level, Output, Speed};

#[embassy_executor::main]
async fn main(_spawner: Spawner) {
    let p = embassy_stm32::init(Default::default());

    // Use pins.rs mapping
    let mut led = Output::new(p.PA4, Level::Low, Speed::Low);

    loop {
        led.toggle();
        Timer::after(Duration::from_millis(500)).await;
    }
}
```

## 5. Preventing Pin Drift in Teams & Repositories

- Always run `fusible check` in CI (`.github/workflows/ci.yml`).
- If a developer moves a hardware trace in `hardware/index.tsx`, `fusible check` immediately updates `pins.rs`. If the firmware driver uses a relocated pin, Cargo compilation will catch the type error instantly.
